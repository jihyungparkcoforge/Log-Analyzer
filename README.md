# Log-Analyzer

Reads an application log file and prints a short report of what broke, when it started, and how severe it is.

## Log formats

Two formats are supported (see [`data/README.md`](data/README.md) for the full contract). Both produce the same entries, so the detectors and the report are identical.

**Comma** (the default), one event per line:

```
YYYY-MM-DD HH:MM:SS,LEVEL,service,message
2026-10-19 14:00:17,ERROR,payment-service,Connection timeout to db-primary
```

`LEVEL` is `INFO`, `WARNING` or `ERROR`. The message is everything after the third comma, so it may contain commas.

**JSON Lines** (`json`), one compact object per line with the same fields and timestamp format; extra keys are ignored:

```
{"ts":"2026-10-19 14:00:17","level":"ERROR","service":"payment-service","message":"Connection timeout to db-primary"}
```

Malformed lines (bad timestamp, unknown level, missing fields, blank lines, ...) are skipped and counted, never fatal. The report lists how many were skipped and why.

## Setup

Requires Python 3.12+ and [uv](https://docs.astral.sh/uv/).

```
uv sync
```

## Usage

```
uv run log-analyzer data/sample.log
```

`uv run python -m log_analyzer.reporting data/sample.log` is equivalent.

The log format is chosen in this order: `--format comma|json` if given; otherwise the `"format"` in a sibling `<log file>.metadata.json` if that file exists (this is how `data/sample.log` and `data/sample.jsonl` work); otherwise `comma`. The log's contents are never sniffed, and an unknown format exits `2` without analyzing.

If skipped lines exceed `MALFORMED_THRESHOLD_PERCENT` (a fraction of all lines; default `0.5` = 50%, from `.env`), the CLI prints the observed percent on stderr and aborts unless you confirm in a terminal.

```
uv run log-analyzer data/sample.jsonl
uv run log-analyzer --format json some.jsonl
```

Options:

| Flag | Effect |
|---|---|
| `--format comma\|json` | How to parse each log line. Default: sibling metadata, else comma. |
| `--json PATH` | Also save the report as JSON to `PATH` (same findings and order as the text report, timestamps in ISO 8601). |
| `--summary` | Append an LLM summary of the findings, generated by `src/log_analyzer/detection/summary.py` through the OpenAI Responses API. |
| `--model MODEL` | Model for `--summary`. Defaults to `OPENAI_MODEL`, then `gpt-6-luna`. |

```
uv run log-analyzer data/sample.log --json report.json
uv run log-analyzer data/sample.log --summary
```

`--summary` needs `OPENAI_API_KEY`, for example in a git-ignored `.env` file. It sends the findings, aggregate error counts and up to 12 `ERROR` log lines to the configured provider, so only use it on logs you are allowed to share with that provider. The text report never depends on it.

Set `ENDPOINT` to an HTTPS Responses-compatible API base URL (such as `https://RESOURCE.services.ai.azure.com/openai/v1`) or a full URL ending in `/responses`. If omitted, it defaults to `https://api.openai.com/v1/responses`. Azure endpoints use the `api-key` header; other endpoints use Bearer authentication. For Azure, set `OPENAI_MODEL` to the deployment name available on that resource. The CLI automatically reads `.env` from the current working directory. Its `OPENAI_API_KEY`, `ENDPOINT`, `OPENAI_MODEL`, and `MALFORMED_THRESHOLD_PERCENT` values override existing shell variables; unrelated variables are not loaded. An explicit `--model` still takes priority. If `.env` is absent, existing environment variables and defaults are used. Run from the project directory to load the project’s `.env`.

Exit codes: `0` when analysis completes (with or without findings); `1` when `--summary` fails (the report is still printed and any JSON is still saved, with `"summary": null`); `2` for a missing or unreadable log file, an unknown `--format`, a `--json` path that cannot be written, or a malformed-line rate above `MALFORMED_THRESHOLD_PERCENT` without confirmation.

## What the report contains

Findings from two detectors in `src/log_analyzer/detection/`:

- **Repeated error message**: the same `ERROR` message from the same service at least 5 times in a 5-minute window (`warning`), or at least 10 times (`critical`).
- **Error spike**: count `ERROR` events in five-minute windows using only the parsed log. The threshold is `max(10, ceil(median + 3 * 1.4826 * max(MAD, 1)))`, based on the latest 12 non-alert windows. MAD is the median absolute deviation of those counts. At or above the threshold gives `warning`; twice the threshold gives `critical`. With no earlier windows the median is zero, so the default threshold is 10. Zero-error windows within the observed log span count toward the baseline. Alerting windows do not raise the baseline.

Both detectors consume `DetectionInput(result.entries)`. No request counts or external history are needed. These counts describe log events, not failed requests. The first/last windows may be partial; the detector counts what is present without extrapolating missing events. An empty time slot is interpreted as zero observed errors, not proof that the service was healthy. The recent-window baseline does not learn daily seasonality; a recurring nightly burst can still alert.

Each finding shows its severity, type, start time, count, service, message and the detector's description. Findings are sorted `critical` before `warning`; equal severities are ordered by start time, then detector, service and message, so the output is deterministic. With no findings the report says `No findings detected.`
